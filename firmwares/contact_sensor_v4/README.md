# contact_sensor_v4

Независимое обслуживание четырёх CS1237 на VBCoreG4, STM32G474RETx.
Основа: [v3](../contact_sensor_v3/contact_sensor_v3.ino).
Требования: [этап 5](../../FSMLocomotion/documents/5-contact_sensor_recovery.md).
Результаты программных проверок и незавершённая аппаратная приёмка:
[validation.md](validation.md).

## Подключение и сборка

| Индекс | Канал | DOUT | SCLK |
|---|---|---|---|
| 0 | R1 | PC9 | PA8 |
| 1 | L1 | PC6 | PC7 |
| 2 | R2 | PB14 | PB13 |
| 3 | L2 | PB10 | PB11 |

Зависимости: STM32 Arduino Core 2.8.1,
[VBCoreG4_arduino_system](https://github.com/VBCores/VBCoreG4_arduino_system)
0.1.0. Используется Generic G474RETx, UART `Serial`, USB выключен.
У этой конфигурации ядра TX=PA2, RX=PA3. Подключение к ПК через внешний
UART-адаптер, 250000 бод, 8N1, общая земля. USB CDC не используется.
Дополнительная библиотека CS1237 не требуется.

Команды из корня репозитория (Arduino CLI должен быть доступен в PATH):

```bash
arduino-cli compile \
  --fqbn 'STMicroelectronics:stm32:GenG4:pnum=GENERIC_G474RETX,xserial=generic,usb=none,xusb=FS,opt=osstd,dbg=none,rtlib=nano,upload_method=swdMethod' \
  --build-path /tmp/mors_contact_v4_build firmwares/contact_sensor_v4

arduino-cli upload \
  --fqbn 'STMicroelectronics:stm32:GenG4:pnum=GENERIC_G474RETX,xserial=generic,usb=none,xusb=FS,opt=osstd,dbg=none,rtlib=nano,upload_method=swdMethod' \
  --input-dir /tmp/mors_contact_v4_build firmwares/contact_sensor_v4
```

Загрузка: ST-Link по SWD, установленный STM32CubeProgrammer.
Эквивалентные параметры доступны в Arduino IDE. Устанавливать v4 вместе
с обновлённым `ContactSensor`; v2 и v3 остаются без изменений.

DOUT настроен как `INPUT_PULLUP`. Подтяжка восстанавливается после каждой
смены направления при конфигурировании. В STM32 Core 2.8.1 `attachInterrupt`
сохраняет PUPDR. На плате обязательно проверить уровни питания/логики АЦП,
совместимость с подтяжкой к питанию GPIO STM32, HIGH при отключённом кабеле
и отсутствие ложных DRDY. Программные тесты электрическую проверку не заменяют.

## Протокол и данные

Кадр 15 байт:

```
"#01" + R1,L1,R2,L2 (int16 LE) + CRC16 (BE) + "\r\n"
```

CRC-16/CCITT-FALSE: первые 11 байт, init=0xFFFF, poly=0x1021,
без отражения и финального XOR. Недостоверный канал: `int16(-1)`, `FF FF`.
Исправная медиана вычисляется по полным signed 24-bit отсчётам. После
отбрасывания младших восьми бит исправный код `-1` заменяется на `-2`.
Маркер не проходит через фильтр и сдвиг.

Кадры формируются независимо от готовности датчиков с частотой 600 Гц;
первый кадр идёт в первом проходе `loop()`. Используется дробный остаток
расписания. После задержки отправляется один актуальный снимок,
пропущенные периоды учитываются счётчиком. При нехватке 15 свободных байт
UART-буфера весь кадр пропускается. Текст в UART не передаётся.

Параметры АЦП: 640 Гц, PGA=128, канал A. Повтор последнего результата разрешён
только до возраста выбранного медианой отсчёта 7 мс. Возраст DRDY до чтения
ограничен 500 мкс, span медианы 4 мс. Недействительность фиксируется до
нового полного окна, поэтому оборот DWT не возвращает старые данные в поток.

## Восстановление и диагностика

Для каждого канала отдельно: PowerDown, ожидание DRDY, чтение/запись
конфигурации, четыре переходных отсчёта, проверка конфигурации, прогрев
медианы из трёх отсчётов, работа. Ожидания выполняются по состояниям;
атомарны только короткие битовые транзакции. После рабочих чтений и отправки
выполняется один шаг восстановления, каналы обслуживаются по кругу.

| Параметр | Значение |
|---|---|
| Рабочий timeout свежих чтений | 20 мс |
| Первый DRDY после PowerDown | 400 мс |
| DRDY между конфигурационными транзакциями | 200 мс, как в v3 |
| Повтор после неудачи | 100, 200, 400, 800, далее 1000 мс |
| PowerDown HIGH / LOW после него | 120 / 12 мкс |
| Сброс backoff | После полного прогрева и перехода в работу |

Ошибки закрытия кадра, reserved status и неожиданный config update запускают
полную повторную настройку только этого АЦП. Потерянный/старый DRDY
отбрасывается с перевооружением EXTI; отсутствие успешных чтений приводит
к рабочему timeout. Повторные попытки не ограничены. Программного управления питанием АЦП нет;
автоматический возврат относится к обмену, восстанавливаемому через SCLK.

Доступно в отладчике:

- `cs1237Channels[i]`: фаза, сроки, уровень backoff, достоверность фильтра;
- `cs1237ReadyStates[i]`: состояние EXTI, время DRDY;
- `cs1237Diagnostics[i]`: счётчики v3, `recoveryAttempts`,
  `successfulRecoveries` (включает первый успешный запуск), `lastError`;
- `medianOutputs`: число новых результатов, включая одинаковые по значению;
- `contactFramesFormed`: реально сформированные снимки;
- `contactFramesSent`: кадры, переданные целиком в UART-буфер;
- `contactFramesSkipped`: пропущенные периоды и кадры без места в буфере.

`lastError` хранит последнюю ошибку, после восстановления не очищается.
Коды соответствуют `ChannelError` в прошивке. Проверять скорость по разности
счётчиков с учётом беззнакового переполнения; числовые изменения силы
не являются счётчиком новых измерений.

## ContactSensor и совместимость

Каждый корректный serial-кадр вызывает одну публикацию LCM, включая
калибровку и четыре отказавших канала. Калибровка поканальная, только по
достоверным данным, 100 отсчётов согласно текущему `sensors.yaml`.
Ноги должны быть разгружены при первоначальной калибровке каждого канала.
Последний калибровочный отсчёт ещё недостоверен для публикации.

Для отсутствующего или неготового канала `raw_data=-1.0f`,
`contact_states=false`. У готового сохраняются делитель 55.0,
вычитание нуля, модуль и существующие пороги 6.0.
Незавершённая калибровка пропавшего канала сбрасывается, завершённый ноль
сохраняется при отказах и переподключении порта в рамках процесса.
После перезапуска процесса калибровка начинается заново.

При ошибке ввода-вывода сразу, при отсутствии корректных кадров через 100 мс
публикуются четыре маркера. Fallback повторяется через 100 мс. CRC-ошибки
не продлевают свежесть и не участвуют в калибровке.

Формат v3 тот же, но настоящий отсчёт `-1` v3 неотличим от маркера v4.
Автоопределения версии нет. Схема LCM не меняется. Потребитель проверяет
`raw_data[i] != -1.0f` и свежесть сообщений; булевы контакты сами по себе
не показывают исправность. Существующий `robot_mode_controller` проверяет
только поступление потока и не обнаруживает частичный отказ v4.
Реакция FSM относится к этапу 6.

## Проверка перед приёмкой

Автоматические проверки драйвера и реального кода `.ino` на хосте:

```bash
cmake -S ContactSensor -B ContactSensor/build -DBUILD_TESTING=ON
cmake --build ContactSensor/build -j2
ctest --test-dir ContactSensor/build --output-on-failure
```

`firmware_test` подменяет GPIO/EXTI/UART и часы. `integration_test` запускает
настоящий драйвер с PTY и LCM multicast на том же ПК; реальный UART не нужен.
Если используется закрытый контейнер, разрешить локальный multicast.

Аппаратная приёмка выполняется пользователем. Записывать условия нагрузки ПК,
serial-приём и LCM-приём, показания отладочных счётчиков и временные метки.
Для каждого опыта заполнить строку в [отчёте](validation.md):

1. Все 16 сочетаний подключённых датчиков при включении, включая ни одного.
   Проверить запуск потока до 10 мс от первого `loop()`.
2. Отстыковка каждого кабеля, одновременный отказ двух и трёх каналов,
   последовательное возвращение. Проверить оставшиеся каналы и справедливость
   повторных попыток.
3. Повторные разрывы и дребезг. Проверить отсутствие зависаний и общих сбросов,
   своевременный маркер вместо старых данных.
4. Отключение/возврат внешнего UART-адаптера на ПК, прекращение чтения порта.
   Проверить продолжение измерений MCU, fallback и переподключение драйвера.
5. Один отключённый датчик в течение 30 минут. Остальные работают всё время.
6. Возврат ранее откалиброванного канала под нагрузкой. Ноль сохраняется.
   Первоначальное подключение некалиброванного канала проверять без нагрузки.
7. При четырёх исправных каналах сравнить знак serial-данных, масштаб,
   ноль и пороги с v3 с учётом замены исправного кода `-1` на `-2`.

В каждом секундном окне нужны 570..630 serial-кадров, не менее 570 новых
медиан на исправный прогретый канал; разрыв между кадрами до 5 мс.
После возраста 7 мс маркер должен попасть в следующий кадр. Ошибка транзакции
делает канал недостоверным к следующему кадру. Возврат устойчивого обмена
в serial до 2 с; для первого подключения отдельно учесть калибровку ПК.
Подтвердить соответствие принятых корректных кадров публикациям LCM,
отдельно измерить потери приёма и доставки.

Без аппаратных результатов этап 5 не завершён.

# Техническое задание на разработку модуля картографирования `HeightMapBuilder` для квадрупедного робота

## 1. Назначение модуля

Модуль `HeightMapBuilder` предназначен для построения локальной 2.5D-карты высот по `depth image`, вычисления карты проходимости (`traversability map`) и публикации результата в LCM для последующего использования в модулях локомоции, планирования шагов и навигации.

Алгоритмическая основа модуля должна быть реализована по мотивам статьи **D. Kim et al., “Vision Aided Dynamic Exploration of Unstructured Terrain with a Small-Scale Quadruped Robot”**: точки из depth-камеры переводятся в мировую систему координат, затем строится 2.5D `heightmap`, применяется морфологическая фильтрация типа `opening`, вычисляется `gradient map`, после чего формируется `traversability map` с дискретными классами проходимости.

Дополнительным обязательным требованием является сохранение ранее наблюденных высот в карте, даже если соответствующая область временно вышла из поля зрения камеры.

---

## 2. Цель разработки

Разработать отдельный высокопроизводительный модуль `HeightMapBuilder`, который:

- получает `depth image` из LCM-канала `DEPTH_IMAGE`;
- получает текущее положение и ориентацию робота из LCM-канала `ROBOT_STATE`;
- преобразует `depth image` в карту высот;
- строит `traversability map`;
- хранит накопленную карту с сохранением ранее наблюденных высот;
- публикует компактное сообщение `heightmap_msg` в LCM-канал `HEIGHTMAP`.

---

## 3. Входные и выходные интерфейсы

### 3.1. Входные данные

#### 3.1.1. Канал depth image

Основным источником визуальных данных является LCM-канал:

- **канал:** `DEPTH_IMAGE`
- **тип сообщения:** `depth_image_msg`
- **расположение описания типа:** `mors_mpc/lcm_msgs`

Сообщение должно содержать `depth image` и связанный с ним `timestamp`.

#### 3.1.2. Канал состояния робота

Текущее положение и ориентация робота должны браться из LCM-канала:

- **канал:** `ROBOT_STATE`

Модуль `HeightMapBuilder` должен извлекать из `ROBOT_STATE` как минимум:

- положение робота в мире: `x`, `y`, `z`;
- ориентацию робота в мире: quaternion, rotation matrix или Euler angles;
- угол `yaw` или данные, достаточные для его вычисления;
- `timestamp` состояния.

Если в `ROBOT_STATE` `yaw` явно не передается, он должен вычисляться из полной ориентации робота.

#### 3.1.3. Калибровочные и конфигурационные данные

Модуль должен использовать:

- intrinsics depth-камеры;
- матрицу калибровки `T_body_camera`;
- параметры карты, фильтрации и классификации из конфигурационного файла  
  `mors_mpc/config/heightmap_builder.yaml`.

### 3.2. Выходные данные

Результат должен публиковаться в LCM-канал:

- **канал:** `HEIGHTMAP`
- **тип сообщения:** `heightmap_msg`

В канал `HEIGHTMAP` должно отправляться только компактное сообщение, содержащее:

- двумерный массив карты;
- текущую координату опубликованного окна;
- текущий угол `yaw`.

`resolution`, размеры окна, схема упаковки и правила декодирования должны быть заранее согласованы между отправителем и получателем и задаваться через конфигурацию, а не передаваться в каждом сообщении.

## 6. Алгоритм работы модуля

Алгоритм должен следовать следующей последовательности обработки.

### 6.1. Получение входных данных

На каждом цикле обработки модуль должен:

1. получить `depth_image_msg` из канала `DEPTH_IMAGE`;
2. получить актуальное сообщение из канала `ROBOT_STATE`;
3. извлечь `timestamp` depth image и `timestamp` состояния;
4. извлечь intrinsics камеры;
5. использовать калибровку `T_body_camera`.

### 6.2. Предобработка depth image

До построения карты необходимо выполнить:

- отбрасывание невалидных пикселей;
- отбрасывание слишком близких и слишком далеких значений;
- подавление явных выбросов;
- опциональное `downsampling` для повышения производительности.

### 6.3. Восстановление 3D-точек в системе камеры

Для каждого валидного depth-пикселя необходимо восстановить 3D-точку в системе координат камеры по intrinsics depth-камеры.

Этот шаг должен быть реализован на CUDA.

### 6.4. Преобразование точек в world frame

Для каждой точки должно быть выполнено преобразование:

```text
camera -> body -> world
```

Текущая поза робота должна браться из `ROBOT_STATE`.

### 6.5. Построение 2.5D heightmap

Плоскость `X-Y` должна быть дискретизирована в регулярную сетку. Для каждой ячейки записывается значение высоты `Z`.

Все следующие параметры должны быть конфигурируемыми:

- размер ячейки;
- размеры внутренней карты;
- размеры публикуемого локального окна;
- диапазон допустимых высот;
- правило обновления ячейки.

### 6.6. Обновление накопленной карты

Модуль должен поддерживать **внутреннюю накопленную карту**, а не только карту по текущему кадру.

Требования:

- ранее наблюденные значения высот должны сохраняться;
- если область временно вышла из поля зрения камеры, ее значения не должны обнуляться;
- данные могут быть перезаписаны новыми наблюдениями;
- данные могут инвалидироваться по `TTL`;
- должна поддерживаться `rolling map` или эквивалентный механизм сдвига карты относительно робота.

### 6.7. Выделение публикуемого локального окна

Если внутренняя карта имеет большой размер, наружу должен публиковаться только локальный фрагмент вокруг робота.

### 6.8. Фильтрация heightmap

После обновления карты должна выполняться морфологическая фильтрация типа:

```text
opening = erosion -> dilation
```

Размер и форма ядра должны настраиваться через конфиг.

### 6.9. Построение gradient map

На отфильтрованной `heightmap` необходимо вычислить карту градиента.

В качестве базового метода должен использоваться оператор Собеля.

### 6.10. Построение traversability map

На основе `gradient map` и заданных порогов каждой ячейке должен быть присвоен один из следующих классов проходимости:

- `STEPPABLE`
- `UNSTEPPABLE`
- `IMPASSABLE`

Пороговые значения переходов между классами должны настраиваться через конфигурационный файл.

### 6.11. Публикация результата

После построения локального окна и `traversability map` модуль должен упаковать результат в компактное сообщение `heightmap_msg` и отправить его в канал `HEIGHTMAP`.

---

## 7. Требования к каналу `ROBOT_STATE`

Модуль `HeightMapBuilder` должен использовать `ROBOT_STATE` как источник текущего положения и ориентации робота.

Сообщение `ROBOT_STATE` должно предоставлять данные, достаточные для вычисления преобразования `T_world_body`, а именно:

- `p_world_body = [x, y, z]`;
- `R_world_body` или quaternion `q_world_body`;
- `timestamp`.

Если в проекте уже принят конкретный тип `robot_state_msg`, модуль обязан использовать его без дублирования аналогичного состояния в отдельных каналах.

При наличии рассинхронизации между `DEPTH_IMAGE` и `ROBOT_STATE` модуль должен выбирать ближайшее по времени состояние в пределах допустимого окна `max_sync_dt`, задаваемого в конфиге.

## 8. Конфигурационный файл

Конфигурационный файл должен лежать строго по пути:

```text
mors_mpc/config/heightmap_builder.yaml
```

Файл должен содержать как минимум следующие группы параметров.

### 8.1. Параметры карты

```yaml
map:
  cell_size: 0.015
  global_size_x: 15.0
  global_size_y: 15.0
  local_window_cells_x: 100
  local_window_cells_y: 100
  height_min: -2.0
  height_max: 2.0
  ttl_sec: 3.0
  update_mode: latest
```

### 8.2. Параметры depth image

```yaml
depth:
  min_depth: 0.10
  max_depth: 3.00
  enable_downsampling: true
  downsample_factor: 2
  remove_outliers: true
```

### 8.3. Extrinsics и синхронизация

```yaml
transforms:
  T_body_camera: [ ... ]

sync:
  max_sync_dt_sec: 0.02
```

### 8.4. Параметры морфологической фильтрации

```yaml
filtering:
  opening_kernel_size: 5
  opening_kernel_shape: ellipse
```

### 8.5. Параметры gradient map

```yaml
gradient:
  method: sobel
  sobel_scale: 1.0
```

### 8.6. Пороги traversability

Пороговые значения для переходов между классами проходимости должны обязательно настраиваться в конфигурационном файле.

```yaml
traversability:
  grad_thr_steppable: 0.05
  grad_thr_unsteppable: 0.12
  unknown_is_impassable: true
```

где:

- при `gradient <= grad_thr_steppable` ячейка относится к классу `STEPPABLE`;
- при `grad_thr_steppable < gradient <= grad_thr_unsteppable` ячейка относится к классу `UNSTEPPABLE`;
- при `gradient > grad_thr_unsteppable` ячейка относится к классу `IMPASSABLE`.

При необходимости допускается расширение логики классификации дополнительными критериями, например по локальному перепаду высот:

```yaml
traversability:
  grad_thr_steppable: 0.05
  grad_thr_unsteppable: 0.12
  unknown_is_impassable: true
  use_height_discontinuity_check: true
  height_step_thr: 0.08
```

## 9. Формат сообщения `heightmap_msg`

Так как требуется минимизировать трафик и передавать только:

- двумерный массив;
- текущую координату;
- `yaw`,

предлагается использовать компактную упаковку одной ячейки в `uint16`.

### 9.1. Кодирование ячейки

Одна ячейка публикуемой карты должна содержать:

- флаг валидности;
- класс проходимости;
- квантованную высоту.

Предлагаемая схема:

- `bit 15` — `valid`
- `bit 14..13` — `traversability_class`
- `bit 12..0` — `height_q`

### 9.2. Значения `traversability_class`

- `00` — `STEPPABLE`
- `01` — `UNSTEPPABLE`
- `10` — `IMPASSABLE`
- `11` — резерв / не используется

### 9.3. Квантование высоты

Высота должна кодироваться с шагом, задаваемым конфигом, например:

```text
height_q = round((height - height_min) / height_resolution)
```

где:

- `height_min`
- `height_resolution`

хранятся в `mors_mpc/config/heightmap_builder.yaml`.

### 9.4. Логическая структура сообщения

```cpp
struct heightmap_msg
{
    float origin_x;
    float origin_y;
    float yaw;
    uint16_t data[H][W];
};
```

где:

- `origin_x`, `origin_y` — координата центра опубликованного окна или его опорной точки;
- `yaw` — текущий `yaw` робота;
- `data` — упакованный двумерный массив.

Размеры `H` и `W`, физический размер ячейки и правила декодирования должны быть известны отправителю и получателю из общего конфига и не должны дублироваться в каждом сообщении.

## 10. Внутреннее представление карты

Во внутреннем представлении модуль должен хранить минимум следующие слои:

- `height_layer`
- `validity_layer`
- `timestamp_layer`

Рекомендуется также хранить:

- `traversability_layer`
- `confidence_layer`
- `observations_count_layer`

Во внешний канал `HEIGHTMAP` должна уходить только компактная упакованная форма.

---

## 11. Требования к CUDA-реализации

CUDA должна использоваться минимум для следующих этапов:

- `depth_to_points.cu` — `depth image -> 3D points`;
- `transform_points.cu` — преобразование `camera -> body -> world`;
- `binning.cu` — запись точек в `heightmap`;
- `morphology_opening.cu` — `erosion + dilation`;
- `sobel_gradient.cu` — вычисление `gradient map`;
- `traversability_classification.cu` — присвоение классов проходимости;
- `local_window_extract.cu` — извлечение локального окна;
- `pack_heightmap_msg.cu` — упаковка карты в формат сообщения.

Требования к производительности:

- предварительное выделение памяти на GPU;
- отсутствие `malloc/free` на каждый кадр;
- использование `pinned host memory` там, где это целесообразно;
- минимизация копирований CPU↔GPU;
- логирование ошибок CUDA.

---

## 12. Требования к надежности и синхронизации

Модуль должен корректно обрабатывать:

- пропуск depth-кадров;
- временное отсутствие `ROBOT_STATE`;
- рассинхронизацию `DEPTH_IMAGE` и `ROBOT_STATE`;
- пустые или поврежденные кадры `depth image`;
- восстановление после временного обрыва LCM-потока.

Если для `depth image` не найдено согласованное по времени состояние из `ROBOT_STATE`, кадр должен либо:

- отбрасываться с логированием причины;
- либо обрабатываться по последнему допустимому состоянию, если это разрешено конфигом.

## 14. Критерии приемки

Модуль считается принятым, если выполнены следующие условия:

1. создана отдельная папка `HeightMapBuilder` внутри проекта `mors_mpc`;
2. реализация выполнена на C++ с использованием CUDA;
3. `depth image` читается из `DEPTH_IMAGE`;
4. положение и ориентация робота берутся из `ROBOT_STATE`;
5. конфигурационный файл расположен по пути `mors_mpc/config/heightmap_builder.yaml`;
6. пороговые значения переходов между классами `traversability` задаются в конфиге;
7. реализован пайплайн:
   - `depth image`,
   - предобработка,
   - 3D reconstruction,
   - `camera -> body -> world`,
   - 2.5D `heightmap`,
   - локальное окно,
   - `opening`,
   - `gradient map`,
   - `traversability map` с классами `STEPPABLE`, `UNSTEPPABLE`, `IMPASSABLE`,
   - публикация;
8. карта сохраняет ранее наблюденные значения, даже если они временно не видны камере;
9. в `HEIGHTMAP` передается только компактное сообщение с двумерным массивом, координатой и `yaw`;
10. документирован формат `heightmap_msg`, структура папок и параметры конфига.

## 15. Примечания по реализации

1. Поскольку требуется минимальный сетевой и вычислительный overhead, внешний формат должен быть жестко компактным, а все дополнительные слои должны храниться только внутри модуля.
2. Для хранения ранее наблюденных участков рекомендуется использовать `rolling global map` и публиковать только локальное окно вокруг робота.
3. Внутренние debug-слои, промежуточные карты и сервисная информация не должны отправляться в основной канал `HEIGHTMAP`.
4. При необходимости расширения функциональности в будущем рекомендуется добавлять отдельные debug-каналы LCM, не изменяя минимальный формат основного сообщения `heightmap_msg`.

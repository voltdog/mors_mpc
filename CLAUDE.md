## Environment

`install.sh` appends an env block to `~/.bashrc`. Every binary depends on it, so a shell without it will fail at startup:

- `CONFIGPATH` — absolute path to `config/`. Almost every process loads its YAML from here. `common/src/Robot.cpp` also resolves the URDF as `$CONFIGPATH/../common/urdf/mors.urdf`, so `CONFIGPATH` must stay a sibling of `common/`.
- `LCM_LOCOMOTION_URL`, `LCM_SERVO_URL` — LCM bus URLs. `GetRequiredEnv()` throws if unset, so a missing var is a hard startup failure, not a warning. `run1.sh` derives both from `LCM_DEFAULT_URL`.
- `/opt/openrobots` on `PATH`/`CMAKE_PREFIX_PATH`/`LD_LIBRARY_PATH` (pinocchio, eiquadprog from robotpkg), `LCM_JAR`, `CLASSPATH` → `lcm_msgs/lcm_types.jar`, `PYTHONPATH` → `lcm_msgs/`, plus `source /opt/ros/jazzy/setup.bash` and `ros_ws/install/setup.bash`.
- `.mpc_venv/` is the Python venv (MuJoCo, numpy, lcm). The launchers call `.mpc_venv/bin/python` explicitly.

**LCM URL naming is inconsistent across the tree.** Active modules (LocomotionController, LocomotionControllerDCM, StateEstimatorHMB, HeightMapBuilder, MorsLogger, BHI360_IMU, ContactSensor, robot_mode_controller, Simulator) use `LCM_LOCOMOTION_URL`/`LCM_SERVO_URL`. Legacy modules (StateEstimator, StateEstimatorMK, StateEstimatorIKZ, StateEstimator1DKF, RealsenseCamera) still use `LCM_CONTROL_URL`/`LCM_VISION_URL`. Check which scheme a module uses before touching its `LcmDataExchange`.

## Build

Each C++ module is a **standalone CMake project** that builds into `<Module>/build`. There is no top-level CMakeLists.

```bash
# One module (the normal case)
cmake -S LocomotionController -B LocomotionController/build -DCMAKE_BUILD_TYPE=Release
cmake --build LocomotionController/build -j"$(nproc)"

# ROS 2 packages
cd ros_ws && colcon build --symlink-install --packages-select robot_mode_controller mors_ros_msgs mors_keyboard_control
source install/setup.bash
```

`./compile_all.sh` builds the ROS packages then loops over a hardcoded `PROJECTS` list (`-c` also runs `cmake ..` first). That list currently contains `WBIC`, which no longer exists, so the script aborts partway with `set -e` — fix the list or build modules individually.

### LCM message types

`.lcm` definitions live in `lcm_msgs/`. **C++ headers are generated per-project at configure time** by `lcm_wrap_types()` over `lcm_msgs/*.lcm`, so a C++ consumer only needs a rebuild. Python and Java bindings are generated separately and must be regenerated by hand after editing a `.lcm` file:

```bash
cd lcm_msgs && bash lcm_gen.sh   # writes mors_msgs/ (Python, gitignored) and lcm_types.jar
```

The Simulator, `plotjuggler`, and `run1.sh`'s `ensure_robot_state_python_binding` all depend on the Python bindings being current.

## Run

The active algorithm is `algorithm:` in `config/robot_config.yaml` (`wbic` | `vision` | `dcm`). It decides both which binaries the launcher starts *and* runtime behaviour inside `LocomotionController` (`vision` enables the heightmap subscriber).

- `./run1.sh [--sim] [--rviz] [--log]` — current launcher. Runs each component in its own process group with staged INT/TERM/KILL cleanup, verifies binaries exist, and regenerates the Python `ROBOT_STATE` binding in sim mode.
- `./run.sh [--rviz] [--log]` — hardware only, `StateEstimatorHMB` + `ContactSensor` + `BHI360_IMU`.
- `./start_controller.sh [--sim] [--rviz] [--log]` — the README path; older hardware stack (`StateEstimator`, `RealsenseCamera`).
- Teleop in a second terminal: `ros2 run mors_keyboard_control mors_keyboard_control`. Wait for `[LocomotionController]: Started` first.
- `--log` starts `MorsLogger`, which writes CSVs to `~/mors_logs/log_<postfix>/` and is auto-killed after 60 s (`run.sh`, `start_controller.sh`) or 120 s (`run1.sh`).

## Architecture

The stack is a set of **independent single-purpose processes glued by LCM**, not a monolith. Each process runs a fixed-rate loop; rates come from `config/timesteps.yaml` and channel names from `config/channels.yaml` (never hardcode a channel name — load it from that file, as every module does).

### Process graph

**Simulation** — `Simulator/mors_simulator.py` (MuJoCo, 1 kHz) is both plant and virtual sensor suite: it publishes `SERVO_STATE`, `IMU_DATA`, `ODOMETRY`, `CONTACT_SENSOR`, `DEPTH_IMAGE` and, because `full_state: True`, ground-truth `ROBOT_STATE` — so **no state estimator runs in sim**. `HeightMapBuilder` consumes `DEPTH_IMAGE` + `ROBOT_STATE` → `HEIGHTMAP`.

**Hardware** — `BHI360_IMU` (HID) → `IMU_DATA`; `ContactSensor` (serial, `/dev/ttyACM0`) → `CONTACT_SENSOR`; `StateEstimatorHMB` → `ROBOT_STATE` + `HEIGHTMAP`.

**Both** — `LocomotionController` (or `LocomotionControllerDCM`) consumes `ROBOT_STATE`, `ROBOT_CMD`, `GAIT_PARAMS`, `ENABLE`, `HEIGHTMAP` and publishes `SERVO_CMD` plus telemetry (`WBC_CMD`, `MPC_CMD`, `GAIT_PHASE`, `WBC_STATE`). `ros_ws/src/robot_mode_controller` is the ROS 2 ↔ LCM bridge: topics `cmd_vel`, `cmd_pose`, `gait_params` and services `robot_mode`, `robot_action` → `ROBOT_CMD` / `GAIT_PARAMS` / `ENABLE`.

### LocomotionController internals

Three loops in one process, communicating through shared state under mutexes:

- **Main loop** (2 ms, `timesteps.yaml: locomotion_controller`) — reads LCM, runs `SimpleGaitScheduler` → `ContactStateFSM` (fuses desired phase with measured contacts and foot vertical velocity to classify `SWING`/`STANCE`/`EARLY_CONTACT`/`LATE_CONTACT`), then `ReferenceGenerator`, `FootStepPlanner` and `SwingController`. Under `vision` the swing controller is fed the heightmap so footholds snap to terrain.
- **`ConvexMPCThread`** (10 ms, `stance_controller_dt`) — convex MPC over a horizon of body states, solved with OSQP; produces reference ground reaction forces for stance legs.
- **`WBICThread`** (1 ms, `wbic_controller_dt`) — whole-body impulse control on the pinocchio model, solved with eiquadprog, prioritised tasks in `src/wbic/tasks/` (body orientation → body position → tip position). Pins itself to a CPU and switches to `SCHED_FIFO`; `realtime_priority` and `cpu_index` are optional `config/wbic.yaml` keys that are absent today, so the `WBICThreadConfig` defaults (priority 75, CPU 3) apply. Emits the joint commands.

`LocomotionControllerDCM` is a fork of this pipeline that adds `DCMGenerator` and `FootStepGenerator` for divergent-component-of-motion gait generation. **Changes made to shared logic must usually be mirrored in both trees** — they do not share source files.

### StateEstimator variants

`StateEstimator`, `StateEstimatorLKF`, `StateEstimatorMK`, `StateEstimatorIKZ`, `StateEstimator1DKF`, `StateEstimatorHMB` are parallel implementations, not layers. **`StateEstimatorHMB` is the active one**; the others are kept for comparison and are mostly wired out of the launchers. HMB deliberately merges what used to be four processes (`RealsenseCamera` T265 pose, `RealsenseCameraD435i` depth, `StateEstimator`, `HeightMapBuilder`) into one multi-threaded binary to remove inter-process LCM latency; LCM is used only at its external boundary. See `StateEstimatorHMB/documents/TZ_state_estimator_hmb.md` for the thread contract.

### Shared code (`common/`)

`structs.hpp` holds the conventions the whole stack assumes: leg order `R1=0, L1=1, R2=2, L2=3`, the `PIN_*` remap to pinocchio joint ordering (`PIN_R1=2, PIN_L1=0, ...`, base at `PIN_START_IDX=7`), axis constants, and the phase-signal enum. `Robot.cpp` builds the pinocchio model, `leg_model.cpp` the analytic leg kinematics, `SimpleGaitScheduler.cpp` the phase clock, `reliable_contact.cpp` the contact filter. `data_types.hpp` carries the WBIC fixed-size Eigen types.

## Gotchas

- **`StateEstimatorHMB` silently degrades.** If `realsense2` is not found, CMake emits a warning and builds a *simulation-only* binary from `sim_main.cpp` with just the heightmap. A green build does not mean the hardware estimator exists.
- **`vbcontrol` is an external dependency** expected at `/home/$USER/vbcontrol` and pulled in with `add_subdirectory`. It is not in this repo; most modules will not configure without it.
- **Eigen ABI must match prebuilt pinocchio.** Any target linking pinocchio defines `EIGEN_MAX_ALIGN_BYTES=16` and `EIGEN_MAX_STATIC_ALIGN_BYTES=16`. Release builds also use `-march=native`; dropping those defines while keeping native AVX flags produces alignment crashes, not compile errors.
- **`kHeightmapCellsX/Y` in `common/include/data_types.hpp` (100×100) must be kept in sync with `map.local_window_cells_x/y` in `config/heightmap_builder.yaml`** — they are compile-time constants on one side and runtime config on the other.
- `.gitignore` excludes `build*` (including `build-safe/`), `lcm_msgs/mors_msgs/`, `tech_req.md`, `AGENTS.md`, `.codex`.
- `config/robot_config.yaml` and `config/state_estimator.yaml` keep hardware and simulation parameter sets side by side with one block commented out. Check which block is live before trusting a value.

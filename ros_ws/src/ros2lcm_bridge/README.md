# ros2lcm_bridge

Двусторонний транспорт ROS 2 ↔ LCM для `FSMLocomotion`, этап 4 плана.
Мост не выбирает переходы FSM, не рассчитывает траектории и не отправляет
`SERVO_CMD` или `ENABLE`. `robot_mode_controller` не изменяется.

## Сборка

После упрощения сообщений используйте чистые каталоги сборки и установки,
чтобы исключить старые сгенерированные типы. `ModeResult` содержит только
`result` и `reason`; поле идентификатора запроса удалено.
ROS2-интерфейсы FSM перенесены в `mors_ros_msgs` вместе с сервисом и action.
Импорты и CLI-типы нужно заменить с `ros2lcm_bridge` на `mors_ros_msgs`.
FSM, мост и потребителей LCM- и ROS2-статуса нужно пересобрать и перезапустить:
LCM- и ROS2-статусы сокращены до семи полей с числовыми фазой и ID модулей.

Из корня репозитория, в окружении ROS 2 Jazzy:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --base-paths ros_ws/src --packages-up-to ros2lcm_bridge \
  --build-base /tmp/mors-bridge-build --install-base /tmp/mors-bridge-install \
  --cmake-args -DPython3_EXECUTABLE=/usr/bin/python3
source /tmp/mors-bridge-install/setup.bash
```

Нужны `lcm-gen`, Python-модули `lcm` и `yaml` (PyYAML), `rclpy`, `geometry_msgs`, генераторы
ROS-интерфейсов. Зависимость `mors_ros_msgs` собирается вместе с мостом.
В Ubuntu 24.04 LCM устанавливается пакетами `liblcm-dev` и `python3-lcm`.
Если локальная база rosdep не содержит `python3-lcm`, установите этот
пакет через apt и используйте `--skip-keys python3-lcm` при запуске rosdep.
LCM-типы генерируются из схем репозитория при сборке и устанавливаются
внутри runtime-модуля моста, отдельно от других Python-пакетов `mors_msgs`.

## Запуск с заглушками

Имена каналов мост и FSM читают из общего `$CONFIGPATH/channels.yaml`. Имя файла фиксировано; параметров выбора файла нет. Переменная `CONFIGPATH` должна указывать на каталог `config` репозитория. В нём заданы `robot_mode_cmd`, `robot_mode_state`, `robot_mode_result`, `robot_cmd` и `gait_params`. Тестовый обмен изолируется отдельным UDP-портом.

Сборка FSM и запуск в первом терминале:

```bash
export CONFIGPATH="$PWD/config"
cmake -S FSMLocomotion -B /tmp/mors-fsm-build -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build /tmp/mors-fsm-build -j2
/tmp/mors-fsm-build/fsm_lcm --stub \
  --url 'udpm://239.255.76.67:17673?ttl=0'
```

Во втором терминале после `source` окружения моста:

```bash
ros2 launch ros2lcm_bridge bridge.launch.py \
  lcm_url:='udpm://239.255.76.67:17673?ttl=0'
```

Не запускайте старый `robot_mode_controller` одновременно с мостом:
совпадают имена сервисов совместимости. Штатный запуск робота этим этапом
не изменяется. Реальные подъём, укладывание и управление приводами относятся
к следующим этапам; сейчас FSM исполняет заглушки.

## ROS-интерфейс

| Имя | Тип | Назначение |
|---|---|---|
| `fsm/command` | `mors_ros_msgs/srv/Command` | Режим, алгоритм, аварийная остановка и сброс аварии |
| `fsm/state` | `mors_ros_msgs/msg/ModeState` | Состояние FSM без транспортных метаданных |
| `fsm/result` | `mors_ros_msgs/msg/ModeResult` | Подтверждения, завершения и локальные ошибки связи |
| `fsm/run_action` | `mors_ros_msgs/action/RunAction` | Именованное действие, статус, отмена и завершение |
| `cmd_vel` | `geometry_msgs/msg/Twist` | Скорость → `ROBOT_CMD` |
| `cmd_vel_stamped` | `geometry_msgs/msg/TwistStamped` | Скорость с проверкой исходного времени |
| `cmd_pose` | `geometry_msgs/msg/Twist` | Поза → полный `ROBOT_CMD` |
| `gait_params` | `mors_ros_msgs/msg/GaitParams` | Параметры → `GAIT_PARAMS` |

Например:

```bash
ros2 topic echo /fsm/state
ros2 topic echo /fsm/result
ros2 service call /fsm/command mors_ros_msgs/srv/Command \
  '{command: {command: 0, target: 2}}'
ros2 action send_goal /fsm/run_action mors_ros_msgs/action/RunAction \
  '{action_id: 0}' --feedback
ros2 service call /fsm/command mors_ros_msgs/srv/Command \
  '{command: {command: 0, target: 3}}'
ros2 topic pub -r 50 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.1}}'
```

`ROBOT_CMD` содержит полный набор уставок. Каждое допустимое сообщение скорости
или позы вызывает одну отправку. Начальные скорость и поза нулевые; затем
сохраняются последние допустимые значения. Скорость включается в пакет только
пока её возраст по монотонным часам не превышает `velocity_timeout` (0.5 с).
После этого обновления позы отправляются с нулевой скоростью. Поза сохраняется
до следующего допустимого обновления. Свежая скорость возобновляет движение.

FSM проверяет общий поток `ROBOT_CMD`. Продолжающийся поток позы поддерживает
свежесть общего потока и сохраняет `LOCOMOTION`, в том числе при нулевой скорости.
Если оба входных потока прекратились, публикации прекращаются и FSM запрашивает
остановку в `BALANCE` по `command_timeout` (0.5 с). Публикации походки этот срок
не продлевают. Периодического повторения сохранённых уставок нет.

Неконечные числа, переполнение float32 и некорректные параметры походки
отбрасываются целиком, не меняют сохранённые уставки и не продлевают свежесть.
`standing` не выбирает режим. Для подписок используется volatile/best-effort,
глубина 1; это совместимо со штатными reliable-публикаторами.

Без метки времени в `Twist` можно контролировать только получение новых
ROS-сообщений. Исходную давность или повторную публикацию сохранённого `Twist`
определить невозможно. Для этого используйте `cmd_vel_stamped`: нулевые,
будущие, просроченные и не возрастающие метки отбрасываются. Часы источника
и ROS-узла должны быть согласованы, включая `use_sim_time`. Используйте один
из двух входов скорости для одного источника управления.

### Запросы и связь

`ModeCommand` содержит только `uint8 command` и `uint8 target`.
Сервис поддерживает `SET_MODE=0`, `SET_ALGORITHM=3`, `ESTOP=4`,
`CLEAR_FAULT=5`, `SET_EXTERNAL=6`. Целевые режимы `SET_MODE`:
`PASSIVE=0`, `BALANCE=2`, `LOCOMOTION=3`. Старый `SET_MODE target=5`
отклоняется и мостом, и FSM. Состояние `EXTERNAL=5` сохранено в статусе.
При `SET_MODE` поле `target` задаёт режим, при `SET_ALGORITHM` задаёт
стабильный ID алгоритма от 0 до 255. Для `ESTOP` и `CLEAR_FAULT` оно
и `SET_EXTERNAL` игнорируется. Например, `{command: {command: 3, target: 0}}` выбирает
алгоритм `stub`. Соответствие ID и фабрики хранится только в FSM;
неизвестный ID отклоняется FSM без изменения выбранного алгоритма.
Добавление алгоритма не требует изменения моста или ROS-сообщения.
`ModeState.algorithm_id` содержит числовой ID выбранного алгоритма.

`SET_EXTERNAL` выбирает единственный внешний адаптер, зарегистрированный
при настройке FSM. Например:

```bash
ros2 service call /fsm/command mors_ros_msgs/srv/Command \
  '{command: {command: 6}}'
```

Из ходьбы FSM сначала останавливается, из `PASSIVE` поднимается,
из действия ждёт безопасного завершения отмены. Передача начинается
из устойчивого `BALANCE`. В состоянии `EXTERNAL` фаза `TRANSFERRING`
означает ожидание подтверждения адаптера и свежего пакета нового сеанса.
Только после этого запрос получает `SUCCEEDED`, а фаза становится `EXTERNAL`.
Повтор не открывает новый сеанс и не продлевает передачу. Для возврата
используйте `SET_MODE` с нужным режимом. При `ESTOP` передача прерывается.

Внешний контроллер задаёт суставные команды через общий выход FSM;
единственным издателем `SERVO_CMD` будет выходной каскад FSM. Сейчас
`stub_external` имитирует время передачи и свежий поток, не формирует
команды приводам. Интерполяция и реальная физическая плавность относятся
к реализации выходного каскада и этими тестами не подтверждаются.

После изменения ROS- и LCM-схем нужна чистая пересборка FSM, моста
и клиентов и перезапуск всех процессов со свежими сгенерированными типами.
Совместимость со старой схемой команды не поддерживается.

Запуск и отмена действий доступны через `fsm/run_action`. Цель `RunAction`
содержит только `uint8 action_id`, feedback содержит `ModeState`, результат содержит
`ModeResult`. LCM-команда отменяет текущее действие единственного клиента.
Команды `START_ACTION=1` и `CANCEL_ACTION=2` в сервисе отклоняются.
ID действия передаётся в LCM `target`; таблица ID и фабрик находится только
в FSM. Заглушки: `0 = stub_action`, `1 = stub_fail`. Неизвестный ID отклоняет FSM.

`ModeResult` содержит два поля:

| Поле | Назначение |
|---|---|
| `result` | Код результата |
| `reason` | Причина отказа, ошибки или неизвестного исхода |

Сервис возвращается после ответа FSM либо истечения срока связи.
`ACCEPTED=0` означает принятие; окончательный результат приходит в
`fsm/result`. Коды `SUCCEEDED=1`, `REJECTED=2`, `BUSY=3`, `CANCELED=4`,
`SUPERSEDED=5`, `TIMEOUT=6`, `FAILED=7` обозначают конечный результат.
Мгновенная операция может сразу вернуть конечный результат.

`UNKNOWN=255` означает неизвестный исход: команда могла быть принята.
Это не `TIMEOUT` FSM и не отмена. Причины: `FSM_UNAVAILABLE`,
`ACK_UNKNOWN`, `RESULT_UNKNOWN`. После таймаута запоздалый ответ нельзя надёжно
связать со следующим запросом того же типа. Мост блокирует новые обычные
команды до перезапуска моста. ESTOP остаётся доступным;
при неизвестном исходе отправляется без обещания подтверждения.

ROS action принимает цель только после `ACCEPTED` или `SUCCEEDED` от FSM.
Отмена завершается после `CANCELED` от FSM и безопасного выхода действия.
Отказ до принятия цели передаётся стандартным отклонением ROS goal;
причина публикуется в `fsm/result`.

LCM-протокол рассчитан на одного клиента. Команда содержит `command`, `target`;
результат — `command`, `result`, `reason`. Поле `command` различает
ответы на запуск действия, отмену и ESTOP. Каждая команда отправляется один раз;
автоматических повторов и параметра `retry_period` больше нет.

Одновременно выполняется одна обычная операция. Отмена и ESTOP могут её
прерывать; дополнительная команда уже ожидающего типа получает `BRIDGE_BUSY`.
Предполагается, что FSM не перезапускается отдельно при работающем мосте.
Мост не обнаруживает перезапуск FSM; командных сеансов и повторов нет.
При перезапуске моста автоматическое восстановление операций не выполняется.

LCM- и ROS2-статус содержат одинаковые семь полей:

| Поле | Тип ROS2 | Назначение |
|---|---|---|
| `current_state`, `target_state` | `int8` | Текущее и целевое состояния |
| `phase` | `int8` | Фаза, константы `PHASE_*` из сообщения |
| `algorithm_id` | `int16` | Выбранный алгоритм, `NO_MODULE=-1` если не выбран |
| `action_id` | `int16` | Подготовленное или выполняемое действие, `NO_MODULE=-1` если отсутствует |
| `fault` | `bool` | Зафиксирована авария |
| `stub_mode` | `bool` | Работа на заглушках |

Допустимые ID модулей: 0–255. Во время восстановления ID действия сохраняется,
после безопасного выхода очищается. Внешний модуль единственный, его имя не
передаётся. Причины аварий и ограничений выводятся в лог FSM.
Коды фаз и их значения приведены в [LCM-интерфейсе](../../../FSMLocomotion/documents/3-lcm_interface.md).

Статусы не кэшируются для новых ROS-подписчиков: QoS reliable/volatile,
глубина 10. Для результатов QoS reliable/volatile, глубина 128.
Свежесть связи определяется по монотонному времени приёма каждого статуса.
Счётчика и сеанса нет, повторные и пришедшие не по порядку статусы не фильтруются.

### Совместимость

При `legacy_services=true` доступны прежние сервисы `RobotCmd`:

| Сервис | `data` | Команда FSM |
|---|---|---|
| `robot_mode` | 0 | `SET_MODE PASSIVE` |
| `robot_mode` | 1 | `SET_MODE LOCOMOTION` |
| `robot_mode` | 2, 3 | `SET_MODE BALANCE` |
| `robot_action` | 1 | `SET_MODE BALANCE`, подъём выполняет FSM |
| `robot_action` | 2 | `SET_MODE PASSIVE`, укладывание выполняет FSM |

`success=1` возвращается после принятия или успеха FSM, `0` после отказа,
`-1` при неизвестном исходе связи. Остальные номера отклоняются. Окончание доступно через `fsm/result`. Старые клиенты не получают
синхронного подтверждения физического завершения.

## Настройки и проверка

Настройки находятся в `config/bridge.yaml`. `lcm_url` по умолчанию берётся из
`LCM_LOCOMOTION_URL`, экспортированной из `~/.bashrc`, как в FSM и
`LocomotionController`. Пустая или отсутствующая переменная без явного URL
приводит к ошибке запуска. Для тестов URL можно задать явно. Префикс
каналов должен совпадать с FSM. `ack_timeout` ограничивает первое
подтверждение, `result_timeout` весь запрос, `state_timeout` свежесть статуса. `velocity_timeout` задаёт срок хранения
ненулевой исходной скорости перед обнулением в очередном полном пакете.
Все эти сроки и polling используют монотонные часы независимо от ROS time.

```bash
colcon test --build-base /tmp/mors-bridge-build --install-base /tmp/mors-bridge-install \
  --packages-select ros2lcm_bridge --event-handlers console_direct+
colcon test-result --test-result-base /tmp/mors-bridge-build/ros2lcm_bridge
FSM_BINARY=/tmp/mors-fsm-build/fsm_lcm /usr/bin/python3 \
  ros_ws/src/ros2lcm_bridge/test/test_integration.py
```

Чтобы включить сквозную проверку в `colcon test`, при сборке задайте
`-DFSM_TEST_BINARY=/tmp/mors-fsm-build/fsm_lcm` в `--cmake-args`.

Интеграционная проверка запускает отдельные процессы FSM и моста, ROS-клиент
и LCM-наблюдатель на отдельном UDP-порту. Команды приводам не отправляются.

Реализация асинхронных action callbacks проверена по
[исходникам rclpy](https://github.com/ros2/rclpy/blob/jazzy/rclpy/rclpy/action/server.py).
